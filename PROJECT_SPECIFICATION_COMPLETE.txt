================================================================================
                        1. PROJECT OVERVIEW & PURPOSE
================================================================================

This is a Restaurant Management & Analytics Platform designed to:

PRIMARY PURPOSE:
- Aggregate data from MULTIPLE offline restaurant software systems
- Provide centralized admin dashboard for restaurant chain management
- Display order, menu, and revenue analytics for all shops
- Export reports (Excel & PDF) for business intelligence

SYSTEM ARCHITECTURE:
- Offline Software (Multiple Locations) → [Data Sync] → Central Online Database
- Admin Dashboard (Online) ← [REST APIs] ← Central Database

TARGET USERS:
- Restaurant Chain Administrators
- Analytics & Reporting Team
- Order Management Staff

================================================================================
                    3. COMPLETE DATABASE SCHEMA
================================================================================

TABLE: SHOPS
Description: Represents multiple restaurant locations in the chain
Columns:
  - SHOP_ID (PK, INT, AUTO_INCREMENT): Unique identifier for shop
  - SHOP_NAME (VARCHAR, NOT NULL): Name of restaurant location
  - LOCATION (VARCHAR, NULLABLE): Address/location of shop
  - CREATED_AT (DATETIME, AUTO_SET): Creation timestamp

Relationships:
  - One-to-Many with ORDERS
  - One-to-Many with MENU

Example Data:
  1, "Maharashtrian Thali - Downtown", "123 Main St, Mumbai", 2025-01-15
  2, "Maharashtrian Thali - Airport", "456 Airport Rd, Mumbai", 2025-01-20
  3, "Maharashtrian Thali - Suburbs", "789 Sub Rd, Pune", 2025-02-01

---

TABLE: MENU_GROUP
Description: Categories/groups for menu items (e.g., Breads, Curries, Desserts)
Columns:
  - GROUP_ID (PK, INT, AUTO_INCREMENT): Unique identifier
  - SHOP_ID (FK, INT, NOT NULL): Foreign key to SHOPS table
  - GROUP_NAME (VARCHAR, NOT NULL): Category name (e.g., "Breads")
  - DESCRIPTION (VARCHAR, NULLABLE): Category description
  - CREATED_AT (DATETIME, AUTO_SET): Creation timestamp
  - UPDATED_AT (DATETIME, AUTO_UPDATE): Last modification timestamp

Relationships:
  - Many-to-One with SHOPS
  - One-to-Many with MENU

Example Data:
  1, 1, "Breads", "Indian bread items", 2025-02-01, 2025-02-01
  2, 1, "Curries", "Gravy-based dishes", 2025-02-01, 2025-02-01
  3, 1, "Desserts", "Sweet items", 2025-02-01, 2025-03-15

---

TABLE: MENU
Description: Individual menu items offered at each shop
Columns:
  - MENU_ID (PK, INT, AUTO_INCREMENT): Unique item identifier
  - SHOP_ID (FK, INT, NOT NULL): Foreign key to SHOPS (which shop this item belongs to)
  - GROUP_ID (FK, INT, NOT NULL): Foreign key to MENU_GROUP
  - ITEM_NAME (VARCHAR, NOT NULL): Name of menu item (e.g., "Butter Naan")
  - PRICE (DECIMAL(10,2), NOT NULL): Price of item
  - IS_ACTIVE (BOOLEAN, DEFAULT true): Whether item is currently available
  - UPDATED_AT (DATETIME, AUTO_UPDATE): Last modification timestamp

Relationships:
  - Many-to-One with SHOPS
  - Many-to-One with MENU_GROUP
  - One-to-Many with ORDER_ITEMS

Example Data:
  1, 1, 1, "Butter Naan", 50.00, true, 2025-02-01
  2, 1, 1, "Garlic Naan", 60.00, true, 2025-02-01
  3, 1, 2, "Butter Chicken", 250.00, true, 2025-02-05
  4, 2, 1, "Butter Naan", 55.00, true, 2025-02-15

---

TABLE: SYSTEM_USERS
Description: Admin users who manage the restaurant
Columns:
  - USER_ID (PK, INT, AUTO_INCREMENT): User identifier
  - USERNAME (VARCHAR, UNIQUE, NOT NULL): Login username
  - PASSWORD (VARCHAR, NOT NULL): Hashed password
  - EMAIL (VARCHAR, NULLABLE): Email address
  - ROLE (VARCHAR, NOT NULL): User role (ADMIN, MANAGER, STAFF) [ENUM: SystemUserRole]
  - SHOP_ID (FK, INT, NULLABLE): Shop assignment (if user manages specific shop)
  - IS_ACTIVE (BOOLEAN, DEFAULT true): Account active status
  - CREATED_AT (DATETIME, AUTO_SET): Creation timestamp

Relationships:
  - One-to-Many with ORDERS (user creates orders)

---

TABLE: ORDERS
Description: Customer orders from any shop
Columns:
  - ORDER_ID (PK, BIGINT, AUTO_INCREMENT): Unique order identifier
  - USER_ID (FK, INT, NOT NULL): Foreign key to SYSTEM_USERS (staff who entered order)
  - SHOP_ID (FK, INT, NOT NULL): Foreign key to SHOPS
  - DEVICE_ORDER_UUID (VARCHAR(100), UNIQUE, NOT NULL): Unique ID from offline device
  - ORDER_TIME (DATETIME, NOT NULL, AUTO_SET): When order was placed
  - PAYMENT_TIME (DATETIME, NULLABLE): When payment was received
  - TOTAL_AMOUNT (DECIMAL(10,2), NOT NULL): Total order value
  - MODE_OF_PAYMENT (VARCHAR, NULLABLE): Payment type [ENUM: CASH, ONLINE]
  - STATUS (VARCHAR, NOT NULL): Order status [ENUM: ACTIVE, PAID, CANCELLED]
  - SOURCE_DEVICE_ID (VARCHAR, NULLABLE): Which offline device created this order
  - SYNC_TIME (DATETIME, AUTO_SET): When synced to online system

Relationships:
  - Many-to-One with SYSTEM_USERS
  - Many-to-One with SHOPS
  - One-to-Many with ORDER_ITEMS

Example Data:
  1, 1, 1, "uuid-001", 2026-04-20 12:30:00, 2026-04-20 12:35:00, 350.00, CASH, PAID, device-1, 2026-04-20 12:40:00
  2, 1, 1, "uuid-002", 2026-04-20 13:00:00, NULL, 500.00, ONLINE, ACTIVE, device-1, 2026-04-20 13:05:00

---

TABLE: ORDER_ITEMS
Description: Individual items within each order
Columns:
  - ORDER_ITEM_ID (PK, INT, AUTO_INCREMENT): Item line identifier
  - ORDER_ID (FK, BIGINT, NOT NULL): Foreign key to ORDERS
  - MENU_ID (FK, INT, NOT NULL): Foreign key to MENU
  - QUANTITY (INT, NOT NULL): How many of this item
  - UNIT_PRICE (DECIMAL(10,2), NOT NULL): Price per unit (at time of order)
  - TOTAL_PRICE (DECIMAL(10,2), NOT NULL): Quantity × Unit Price

Relationships:
  - Many-to-One with ORDERS
  - Many-to-One with MENU

Example Data:
  1, 1, 1, 2, 50.00, 100.00
  2, 1, 3, 1, 250.00, 250.00
  3, 2, 2, 1, 60.00, 60.00

---

TABLE: SYNC_LOG
Description: Tracks data synchronization from offline devices
Columns:
  - SYNC_LOG_ID (PK, INT, AUTO_INCREMENT)
  - SOURCE_DEVICE_ID (VARCHAR): Which offline device synced
  - SHOP_ID (FK, INT): Which shop location
  - SYNC_TIME (DATETIME): When sync occurred
  - RECORDS_SYNCED (INT): How many records were synced
  - STATUS (VARCHAR): SUCCESS, FAILURE, PARTIAL
  - ERROR_MESSAGE (VARCHAR, NULLABLE): If failed, what went wrong

---

TABLE: SYSTEM_LOG
Description: Audit trail of system operations
Columns:
  - LOG_ID (PK, INT, AUTO_INCREMENT)
  - USER_ID (FK, INT): Which user performed action
  - ACTION (VARCHAR): What action (CREATE, UPDATE, DELETE, VIEW)
  - ENTITY_TYPE (VARCHAR): What entity (ORDER, MENU, SHOP)
  - ENTITY_ID (INT/BIGINT): Which entity
  - TIMESTAMP (DATETIME): When action occurred
  - DETAILS (TEXT, NULLABLE): Additional details

================================================================================
                    4. DATA FLOW & INTEGRATION ARCHITECTURE
================================================================================

OFFLINE → ONLINE SYNC FLOW:

  Offline Software (Restaurant)
        ↓
  [Local Database]
  - Orders created locally
  - Menu items managed locally
  - Payment processed locally
        ↓
  [Sync Engine - Built by Offline Software Team]
  - Detects new/modified records
  - Creates sync payload (JSON)
  - Sends to Online APIs via HTTP/HTTPS
        ↓
  Central Online System (This Project)
  [POST /api/orders] ← Receives order data
  [POST /api/admin/menus/{shopId}] ← Receives menu data
        ↓
  [MySQL Database] ← Stores centralized data
        ↓
  [Admin Dashboard] ← Displays aggregated data
        ↓
  Administrators view consolidated reports, analytics, revenue

KEY REQUIREMENTS FOR OFFLINE SOFTWARE:

1. DEVICE IDENTIFICATION
   - Each offline device must have unique SOURCE_DEVICE_ID
   - Used to track which device created which order
   - Helps with debugging sync issues

2. UNIQUE ORDER IDENTIFIERS
   - DEVICE_ORDER_UUID: Unique ID generated by offline device
   - Used to prevent duplicate orders during sync
   - If sync fails and retries, same UUID = skip duplicate

3. BATCH SYNC
   - Offline software should batch multiple orders
   - Send as array in single API call for efficiency
   - Include timestamp when order was created locally

4. TIMESTAMP INTEGRITY
   - Offline device must have accurate local time
   - ORDER_TIME should be when order was placed (local time)
   - SYNC_TIME updated by online system

5. SHOP IDENTIFICATION
   - Offline device knows which SHOP_ID it belongs to
   - Include SHOP_ID in all sync payloads
   - Enables multi-location tracking

                    7. ENUMERATIONS

OrderStatus.java
  - ACTIVE: Order is pending payment/completion
  - PAID: Order has been paid
  - CANCELLED: Order was cancelled

PaymentMode.java
  - CASH: Paid in cash
  - ONLINE: Paid via online methods

                    9. SECURITY DETAILS
================================================================================

AUTHENTICATION:
  - Spring Security 6.x
  - Basic Authentication (username:password)
  - Credentials sent in Authorization header
  - Backend validates against SYSTEM_USERS table

PASSWORD SECURITY:
  - Passwords are hashed using BCryptPasswordEncoder
  - Never store plain text passwords

SESSION MANAGEMENT:
  - Frontend stores JWT/auth token in localStorage
  - Token sent with every API request via Axios interceptor
  - Authorization header: "Authorization: Bearer {token}"

AUTHORIZATION:
  - Role-based access control (RBAC)
  - @PreAuthorize("hasRole('ADMIN')") on admin endpoints
  - Only ADMIN users can access /api/admin/** endpoints

CORS CONFIGURATION:
  - Configured to allow requests from React frontend
  - Frontend runs on port 5173 (dev) or different domain (prod)
  - Backend exposes APIs on port 8080

HTTPS (PRODUCTION):
  - Should use HTTPS for deployment
  - SSL/TLS certificates required
  - Enforce API authentication and encryption

   spring.datasource.url=jdbc:mysql://localhost:3306/maharashtrian_thali
   spring.datasource.username=root
   spring.datasource.password=root

3. Hibernate will create tables automatically on first run (ddl-auto=update)
   OR validate existing tables (ddl-auto=validate)

BACKEND SETUP & RUN:
1. Navigate to Backend folder:
   cd Backend

   ./mvnw clean install

3. Run Spring Boot application:
   ./mvnw spring-boot:run

   Backend will start at: http://localhost:8080
   API endpoints available at: http://localhost:8080/api/**

FRONTEND SETUP & RUN:
1. Navigate to Frontend folder:
   cd Frontend

2. Install dependencies:
   npm install

3. Run development server:
   npm run dev

   Frontend will start at: http://localhost:5173

4. Access in browser:
   http://localhost:5173/login
   Login with admin credentials

PRODUCTION BUILD:
1. Backend:
   ./mvnw clean package

                    11. REQUIREMENTS FOR OFFLINE SOFTWARE
================================================================================

CRITICAL INTEGRATION REQUIREMENTS:

1. SYNC ARCHITECTURE:
   - Offline software must have local database with same schema
   - Implement sync engine to periodically push data to online system
   - Use REST APIs to POST orders and menu items

2. DATA MAPPING:
   - Offline device must map its local data to online schema
   - Example: Map "Device Order ID" → "deviceOrderUuid"
   - Ensure SHOP_ID matches between offline and online

3. UNIQUE IDENTIFIERS:
   - Generate DEVICE_ORDER_UUID (e.g., UUID v4) for each order
   - Use SOURCE_DEVICE_ID to identify which device created data
   - Prevents duplicates during retry scenarios

4. TIMESTAMP REQUIREMENTS:
   - Offline device must have accurate system time
   - Include ORDER_TIME as when order was placed
   - Online system will set SYNC_TIME upon receipt

5. ERROR HANDLING:
   - Offline software should:
     * Retry failed API calls (exponential backoff)
     * Queue orders if internet unavailable
     * Sync when connection restored
     * Log all sync attempts for debugging

6. API INTEGRATION ENDPOINTS TO USE:
   - POST /api/orders (to send order data)
   - POST /api/admin/menus/{shopId} (to sync menu items)
   - POST /api/admin/menu-groups/shop/{shopId} (to sync categories)
   - Other GET endpoints for verification/sync validation

7. AUTHENTICATION:
   - Offline software must authenticate using valid admin credentials
   - Store credentials securely (not hardcoded)
   - Use same authentication mechanism as online system

8. DATA VALIDATION:
   - Validate all data before sending
   - Ensure prices are positive
   - Verify shop IDs exist
   - Check item quantities > 0

9. BATCH OPERATIONS:
   - Batch multiple orders into single API call if possible
   - Reduces network overhead
   - More efficient processing

10. MONITORING & LOGGING:
    - Log all sync activities
    - Capture error details for troubleshooting
    - Monitor sync frequency and success rates
    - Alert on repeated failures

TROUBLESHOOTING:

1. Database connection fails:

   - Verify connection string in application.properties
   - Ensure database exists and credentials are correct

2. CORS errors:
   - Check backend CORS configuration
   - Verify frontend URL is whitelisted
   - Ensure credentials are included in requests

3. API returns 401 Unauthorized:
   - Check authentication credentials
   - Verify token is included in headers
   - Ensure user has ADMIN role

4. Port conflicts:
   - Backend: Change server.port in application.properties
   - Frontend: Change port in vite.config.js
