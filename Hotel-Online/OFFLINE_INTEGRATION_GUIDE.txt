================================================================================
                    1. SYSTEM OVERVIEW
================================================================================

YOUR SOFTWARE:
- Runs locally at each restaurant location (offline-first)
- Has local database for orders, menus, inventory
- Can work without internet connection
- Main purpose: POS (Point of Sale) / Restaurant Management

CENTRAL ONLINE SYSTEM (Our System):
- Cloud-based admin dashboard
- Aggregates data from ALL restaurant locations
- Provides analytics and reporting
- Multi-location chain management
- Accessible to administrators anywhere

INTEGRATION GOAL:
Sync your local restaurant data to central online system so that:
- Administrators can see orders from all shops in one dashboard
- Revenue analytics are consolidated
- Menu items can be centrally managed
- Reports can be generated for entire chain

================================================================================
                    3. DATA SYNC FLOW
================================================================================

SCENARIO 1: REAL-TIME ORDER SYNC
1. Customer places order at your POS
2. Order stored in your local database
3. Your sync engine detects new order
4. Your app calls: POST /api/orders
5. Order data sent to central system
6. Central system stores in online database
7. Admin can view order in dashboard
8. Log entry created for sync event

SCENARIO 2: PERIODIC MENU SYNC
1. Admin updates menu at your restaurant
2. Changes saved to local database
3. Your sync engine runs (e.g., every 30 minutes)
4. Detects changed menu items
5. Your app calls: POST /api/admin/menus/{shopId}
6. Menu data sent to central system
7. Online dashboard reflects changes

SCENARIO 3: OFFLINE WITH QUEUE
1. Internet is down at restaurant
2. Orders continue to be created locally
3. Your offline queue stores orders
4. Internet comes back online
5. Your sync engine retries queued data
6. All queued orders synced to central system

================================================================================
                    4. YOUR SYNC ENGINE - WHAT TO BUILD
================================================================================

MINIMUM REQUIREMENTS:

1. CONFIGURATION:
   - Store central system URL (configurable)
   - Store authentication credentials (encrypted)
   - Store your SHOP_ID (identifier at central system)
   - Store unique DEVICE_ID for this location

2. ORDER SYNC:
   - Monitor local ORDER table for new/unsynced orders
   - Build JSON payload from order data
   - POST to central system: /api/orders
   - Mark order as synced on success
   - Log error on failure, retry later

3. MENU SYNC:
   - Monitor local MENU table for new/changed items
   - Build JSON payload from menu item data
   - POST to central system: /api/admin/menus/{shopId}
   - Mark item as synced
   - Handle errors and retry

4. ERROR HANDLING:
   - Network disconnection: Queue for retry
   - Invalid data: Log error, don't retry (fix locally first)
   - Server error (500): Retry with exponential backoff
   - Authentication error (401): Check credentials
   - Retry up to 5 times with increasing delays (1s, 2s, 4s, 8s, 16s)

5. LOGGING:
   - Log all sync attempts with timestamp
   - Log successes and failures
   - Store error messages for debugging
   - Keep 30 days of sync history

6. SCHEDULING:
   - Sync orders: Every 1-5 minutes (or real-time if possible)
   - Sync menus: Every 15-30 minutes
   - Off-peak sync: Higher frequency during slow hours
   - Full resync: Daily at midnight

OPTIONAL ENHANCEMENTS:
- Bidirectional sync (pull menu updates from central)
- Conflict resolution (if local and remote data differ)
- Selective sync by shop or category
- Manual sync trigger in UI
- Sync status dashboard in your app

                    5. DATABASE SCHEMA MAPPING
================================================================================

YOUR LOCAL DATABASE → CENTRAL ONLINE SYSTEM

YOUR TABLE: orders
  local_order_id → (offline only, don't sync)
  order_uuid → DEVICE_ORDER_UUID (MUST be unique)
  shop_id → SHOP_ID (must match central system shop ID)
  user_id/staff_id → USER_ID (authenticated staff)
  order_timestamp → ORDER_TIME
  total_amount → TOTAL_AMOUNT
  payment_method → MODE_OF_PAYMENT (CASH or ONLINE)
  payment_timestamp → PAYMENT_TIME
  status → STATUS (ACTIVE, PAID, CANCELLED)
  device_id → SOURCE_DEVICE_ID (your device/location identifier)
  sync_status → (your app only, 0=not synced, 1=synced)

YOUR TABLE: order_items
  item_id → ORDER_ITEM_ID
  order_id → ORDER_ID (reference)
  menu_id → MENU_ID (must match central system menu IDs)
  quantity → QUANTITY
  price_per_unit → UNIT_PRICE
  (total calculated) → TOTAL_PRICE

YOUR TABLE: menu_items
  menu_id → MENU_ID (must be consistent)
  shop_id → SHOP_ID
  category_id → GROUP_ID
  item_name → ITEM_NAME
  price → PRICE
  is_available → IS_ACTIVE
  last_modified → UPDATED_AT
  sync_status → (your app only)

YOUR TABLE: menu_categories
  category_id → GROUP_ID
  shop_id → SHOP_ID
  category_name → GROUP_NAME
  description → DESCRIPTION

IMPORTANT:
- SHOP_ID must match the ID in central system
  Example: "Downtown" location = SHOP_ID 1 at central
- MENU_IDs should be globally unique or prefixed by shop
  Example: Menu 1001 = shop 1, item 1; Menu 1002 = shop 1, item 2
- DEVICE_ORDER_UUID should be unique for every order
  Generate using: UUID.randomUUID() or similar
- SOURCE_DEVICE_ID identifies your device/location
  Example: "device-downtown-pos-1" or MAC address

                    7. PRACTICAL SYNC ENGINE EXAMPLE
================================================================================

PSEUDOCODE FOR SYNC ENGINE:

```
SYNC_ENGINE:
  
  Every 5 minutes:
    1. Get unsynced orders from local database
    2. For each order:
       a. Build JSON payload
       b. Call POST /api/orders
       c. If success (200-201):
          - Mark order as synced in local database
          - Log success
       d. If error 409 (duplicate):
          - Mark order as synced (already exists at central)
          - Log duplicate, no retry needed
       e. If error 400 (bad request):
          - Log error with order ID
          - Don't retry (fix locally)
          </blockquote>If network error or 500:
          - Retry after 1 minute (max 5 times)
          - Use exponential backoff: 1s, 2s, 4s, 8s, 16s
    
    3. Get modified menu items (updated in last 5 minutes)
    4. For each menu item:
       a. Check if category exists at central, create if needed
       b. Determine if new or update (via sync_status flag)
       c. Call POST (new) or PUT (update)
       d. Mark as synced on success
       e. Retry on network errors
    
    5. Log all activities to sync_log table

ON NETWORK RECONNECTION:
  1. Detect internet is back online
  2. Immediately trigger sync_engine
  3. Process all queued data
  4. Send any failed items with retries

CONFLICT RESOLUTION:
  If central system has newer data:
    - Your local data is outdated
    - Option 1: Overwrite locally with central data
    - Option 2: Alert admin to manual review
    - Option 3: Mark as synced and move on

ERROR HANDLING:
  200-299: Success, mark as synced
  4xx: Client error, log and don't retry (except 409)
  5xx or network: Retry with backoff
  409: Conflict/duplicate, mark as synced, no retry
```

CODE EXAMPLE (Python):

```python
import requests
import json
import uuid
from datetime import datetime
import base64
import time

class RestaurantSyncEngine:
    def __init__(self, central_url, shop_id, device_id, username, password):
        self.central_url = central_url
        self.shop_id = shop_id
        self.device_id = device_id
        self.auth = (username, password)
        self.max_retries = 5
        self.base_retry_delay = 1
    
    def sync_orders(self, orders):
        """Sync unsynced orders to central system"""
        for order in orders:
            payload = {
                "deviceOrderUuid": self.generate_order_uuid(order),
                "userId": order.get('user_id'),
                "shopId": self.shop_id,
                "orderTime": order.get('order_time'),
                "totalAmount": float(order.get('total_amount')),
                "modeOfPayment": order.get('payment_method'),
                "sourceDeviceId": self.device_id,
                "orderItems": order.get('items', [])
            }
            
            retry_count = 0
            while retry_count < self.max_retries:
                try:
                    response = requests.post(
                        f"{self.central_url}/api/orders",
                        json=payload,
                        auth=self.auth,
                        timeout=30
                    )
                    
                    if response.status_code in [200, 201]:
                        print(f"Order {order['id']} synced successfully")
                        self.mark_order_synced(order['id'])
                        break
                    
                    elif response.status_code == 409:
                        print(f"Order {order['id']} duplicate, marking as synced")
                        self.mark_order_synced(order['id'])
                        break
                    
                    elif response.status_code == 400:
                        print(f"Bad request for order {order['id']}: {response.text}")
                        self.log_error(order['id'], response.text)
                        break
                    
                    elif response.status_code >= 500:
                        print(f"Server error, retry {retry_count + 1}/{self.max_retries}")
                        retry_count += 1
                        if retry_count < self.max_retries:
                            time.sleep(self.base_retry_delay ** retry_count)
                    
                    else:
                        print(f"Unknown error: {response.status_code}")
                        break
                
                except requests.exceptions.RequestException as e:
                    print(f"Network error: {e}, retry {retry_count + 1}/{self.max_retries}")
                    retry_count += 1
                    if retry_count < self.max_retries:
                        time.sleep(self.base_retry_delay ** retry_count)
    
    def generate_order_uuid(self, order):
        """Generate unique order UUID"""
        timestamp = datetime.now().strftime("%Y%m%d%H%M%S")
        return f"uuid-{self.shop_id}-{self.device_id}-{timestamp}-{order['id']}"
    
    def mark_order_synced(self, order_id):
```

================================================================================
                    9. TROUBLESHOOTING GUIDE
================================================================================

PROBLEM: "401 Unauthorized"
CAUSES:
  - Wrong username or password
  - Credentials not Base64 encoded correctly
  - Credentials expired or revoked
SOLUTION:
  - Verify credentials from central operator
  - Check Base64 encoding in your code
  - Test with: curl -u username:password <url>
  - Request new credentials if expired

---

PROBLEM: "409 Conflict - Duplicate UUID"
CAUSES:
  - Order with same deviceOrderUuid already exists
  - Manual retry of same order
SOLUTION:
  - This is not an error, mark as synced in your system
  - Don't retry this order again
  - Check if another POS already sent this order

---

PROBLEM: "400 Bad Request - Invalid Shop ID"
CAUSES:
  - SHOP_ID doesn't exist at central system
  - Wrong SHOP_ID in your config
SOLUTION:
  - Verify SHOP_ID from central operator
  - Ensure all orders use correct SHOP_ID
  - Update your config and restart

---

PROBLEM: "No orders appearing in dashboard"
CAUSES:
  - Sync not running at all
  - All orders failing with errors
  - Network connectivity issue
SOLUTION:
  - Check logs for sync errors
  - Verify network can reach central API
  - Check authentication with curl:
    curl -u username:pwd -H "Content-Type: application/json" \
         -d {} https://central-url/api/orders
  - Manually trigger sync from admin panel
  - Check database for unsynced orders

---

PROBLEM: "Network errors / Connection timeout"
CAUSES:
  - Central system is down
  - Internet connectivity issue
  - Firewall blocking connection
  - DNS resolution failure
SOLUTION:
  - Check if central system is operational (status page)
  - Test internet connectivity: ping google.com
  - Check firewall allows outbound HTTPS on port 443
  - Test DNS: nslookup central-url
  - Check for VPN requirements
  - Retry automatically (already implemented)

---

PROBLEM: "Orders synced but not visible in dashboard"
CAUSES:
  - Orders synced but dashboard not refreshed
  - Wrong date filter in dashboard
  - Orders have status ACTIVE (not yet PAID)
SOLUTION:
  - Refresh dashboard page
  - Check date range in dashboard (should include order date)
  - Note: ACTIVE orders show in different view than PAID orders

---

PROBLEM: "Retry keeps happening, sync never completes"
CAUSES:
  - Validation error in order data
  - Incompatible data format
  - Missing required fields
SOLUTION:
  - Check error message in logs
  - Verify all required fields in payload:
    * deviceOrderUuid (must be unique)
    * shopId (must exist)
    * userId (must exist)
    * totalAmount > 0
    * orderItems not empty
  - Check data types match API requirements
  - Stop retrying after fixing local data

4. ORDER STATUS VALIDATION:
   ✓ status is one of: ACTIVE, PAID, CANCELLED
   ✓ PAID orders should have paymentTime set

5. NUMERIC PRECISION:
   ✓ Currency values have max 2 decimal places
   ✓ No currency symbols ($, ₹, etc.)
   ✓ Quantities are positive integers

6. STRING VALIDATION:
   ✓ No null values for required fields
   ✓ Trim whitespace from item names
   ✓ Max lengths respected:
     * itemName: 255 characters
     * deviceOrderUuid: 100 characters

                    11. SECURITY BEST PRACTICES
================================================================================

CREDENTIAL SECURITY:
  ✓ Never hardcode credentials in source code
  ✓ Use environment variables or config files
  ✓ Restrict file permissions (chmod 600)
  ✓ Rotate credentials periodically
  ✓ Monitor credential access logs
  ✓ Use separate credentials per location/device

DATA TRANSMISSION:
  ✓ Always use HTTPS (not HTTP)
  ✓ Verify SSL certificates (don't disable verification)
  ✓ Use TLS 1.2 or higher
  ✓ Don't send sensitive data in logs

LOCAL DATABASE:
  ✓ Encrypt sensitive data (passwords, payment tokens)
  ✓ Restrict database access to application
  ✓ Regular database backups
  ✓ Audit logs for data access

API SECURITY:
  ✓ Validate all API responses
  ✓ Check response status codes and content
  ✓ Don't blindly trust API responses
  ✓ Implement timeout for API calls (30 seconds recommended)
  ✓ Rate limit your API calls (don't overwhelm server)

ERROR LOGGING:
  ✓ Log errors for debugging, NOT sensitive data
  ✓ Don't log full API responses if they contain sensitive info
  ✓ Secure log files (restrict access)
  ✓ Regular log rotation and cleanup
  ✓ Anonymize IP addresses in logs if possible

================================================================================
                    14. FREQUENTLY ASKED QUESTIONS
================================================================================

Q: What if internet is down for a day?
A: Your sync engine queues orders locally and retries when online.
   No data is lost. All queued orders sync when connection restored.

Q: What if order is already synced and we retry?
A: Central system detects duplicate via deviceOrderUuid and rejects (409).
   Your system marks it as synced already. No duplicates created.

Q: Can we use our own order IDs instead of UUIDs?
A: Yes, but IDs must be globally unique. UUIDs are safer.
   Example: shop_id + local_id = 001-001234 (globally unique)

Q: How often should we sync menus?
A: Every 15-30 minutes is good. Real-time sync if you prefer.
   If menu changes rarely, adjust to every hour.

Q: Can multiple locations share the same database?
A: No, each location should have separate SHOP_ID.
   Each SHOP_ID maps to separate location in central system.

Q: What if central API is slow?
A: Sync engine retries automatically.
   Increase timeout from 30s to 60s if needed.
   Contact central system admin if consistently slow.

Q: How do we handle order modifications?
A: Once order is paid/completed, treat as final (no changes).
   If unpaid, sync new order with updated total.
   Implement versioning if needed.

Q: Can customers see their orders in central dashboard?
A: No, only admins. Central system is admin-only for now.
   (May add customer-facing features in future)

Q: How do we handle refunds?
A: Update order status to CANCELLED.
   POST to /api/admin/orders/{orderId}/status with "CANCELLED".
   Sync updated status to central system.

Q: What if we go out of business?
A: Stop sync (no more orders to send).
   Historical data remains in central system for records.
   Other locations continue syncing normally.
